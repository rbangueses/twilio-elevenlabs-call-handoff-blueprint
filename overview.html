What it is

Human escalation for voice agents, owned by Twilio.

ElevenLabs can run the voice-agent conversation. Twilio can own the phone number, Studio journey, TaskRouter routing, Flex task, and downstream contact-center context. This blueprint connects those pieces without relying on a blind transfer as the primary handoff path.

The core move is simple: when Twilio sends the caller to ElevenLabs, it passes the original parent CallSid and caller metadata as dynamic variables. When the agent needs a human, an ElevenLabs webhook tool sends summary, intent, reason, and call identifiers back to a protected Twilio Function. That Function updates the original live call with the next TwiML instruction.

Why it is useful

Keep the handoff structured instead of blind.

Native phone transfer is useful when all you need is to send a caller somewhere else. This pattern is for the moment when the handoff needs to carry operational context.

1

Preserve call control

Twilio updates the original live call, so the handoff can return to Studio or enqueue into TaskRouter without losing the parent call relationship.

2

Pass useful context

The receiving human can get a concise summary, intent, reason, caller number, called number, parent call SID, and handoff ID.

3

Route with Twilio

Use Studio for journey control, Flex for agent experience, or TaskRouter for another Twilio-powered contact center.

When to use

Use it when escalation is part of the customer journey.

Use this blueprint when the AI agent is allowed to solve common issues, but needs a controlled human fallback for account access, billing, compliance, complex support, or explicit requests for a person.

It is especially useful when your Twilio number already starts in Studio, when Flex should receive structured task attributes, or when routing logic needs to stay in TaskRouter instead of inside the voice-agent platform.

Use ElevenLabs native transfer instead when the goal is only to blind-transfer a caller to a phone number or SIP destination and you do not need Twilio-owned context, routing, or Studio return.

How it works

Two routing patterns, one parent-call update.

The same ElevenLabs tool contract can hand the caller back to either Studio or TaskRouter. The difference is the Twilio Function URL the tool calls.

Shared call lifecycle Twilio Functions + ElevenLabs webhook tools
Twilio Voice Caller reaches a Twilio number.
ElevenLabs agent Twilio connects the live call through register-call.
Escalation tool Agent sends summary and call identifiers to Twilio.
Human routing Studio, TaskRouter, or Flex receives the caller.

Pattern A: Studio return

Best when Studio owns IVR, branching, reporting, or Send to Flex.

  • /studio_voice sends the caller to ElevenLabs.
  • /studio_escalate redirects the live call back to the Studio Flow.
  • Studio resumes on the TwiML Redirect return transition.
  • Send to Flex creates the human-agent task.

Pattern B: TaskRouter enqueue

Best when you want the smallest direct handoff to Flex or another TaskRouter-powered contact center.

  • /voice sends the caller to ElevenLabs.
  • /escalate updates the parent call.
  • Twilio returns <Enqueue> with task attributes.
  • TaskRouter routes the voice task to an agent.

Optional memory

Add prior customer context without changing the handoff path.

The optional memory overlay lets the ElevenLabs agent call a Twilio Function to recall relevant customer context from Conversation Memory before responding or escalating.

Because both /voice and /studio_voice already pass the caller number as a dynamic variable, memory does not need a separate voice entrypoint. The tool calls /memory_recall on demand.

Where Orchestrator fits

Conversation Orchestrator can capture conversations and link them to Memory profiles, giving the voice agent useful prior observations and summaries while keeping Twilio in control of routing and escalation.
